Implant API exposed through the HTTP/HTTPS **listener** process. This is not the [team server management REST API](/docs/rest-api/team-server) used by the client and automation.

The implant uses one path per channel: `endpointPath` from the listener profile (normalized by the server to start with `/`, with no trailing slash except `/`). **GET** and **POST** are registered on that path.

<Callout type="info" title="Building a custom implant?">
  We recommend reading the advanced guide on [Custom Implants](/docs/custom-implants), which walks through the implant API. That can save you a lot of trouble.
</Callout>

## Communication encryption

Every request from the implant must be encrypted. This is not optional. The team server always expects an encrypted body.

Encryption uses an AES-256 key shared by the implant and the team server. The key is created when the implant is built and stored in the database so the team server can decrypt incoming requests.

**Important**: every implant request body must contain two parts:

1. **Challenge** - 9 random bytes encrypted with the AES-256 key (always exactly 9 bytes)
2. **Payload** - the request JSON encrypted with the same AES-256 key

The two blobs are concatenated and sent together. For example:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** is the challenge
- `{"output": "123"}` is the payload

The encrypted output would be:

```
000000111111
```

The challenge exists so the listener can find the right key to decrypt the payload. As noted above, the challenge is always 9 bytes. That keeps validation fast without touching the real payload, which is often much larger.

If no key works, the listener returns HTTP `200` with an empty body.

On the wire, each encrypted segment is a **12-byte nonce** followed by **AES-GCM ciphertext including the 16-byte auth tag**. The listener treats the first **37 bytes** (`12 + 9 + 16`) as the probe blob and decrypts the remainder as the payload blob. Both must decrypt with the same key row from the `AesKeys` table.

The minimum POST body size is **65 bytes** (probe segment plus at least one payload byte). Shorter bodies get HTTP `200` with an empty response.

### Request body template (`implantBody`)

When the channel sets `implantBody` (or legacy `beaconBody`), the raw HTTP body must match that template. The marker `§content§` is where the encrypted bytes belong. The listener extracts the substring matched at `§content§` and only that slice is decrypted.

If `implantBody` is empty or exactly `§content§`, the entire raw body is decrypted.

If a non-empty template is configured and the body does not match, the listener returns HTTP `200` with an empty body (no decryption).

### Response body template (`listenerResponse`)

Handler JSON is encrypted into a single blob the same way as implant requests. By default that blob is the entire response body. When `listenerResponse` is set, the encrypted bytes replace `§content§` in that template.

Successful encrypted responses use `Content-Type: application/octet-stream`. The HTTP status is **200** unless noted below.

### Silent HTTP `200` (empty body)

These cases return HTTP **200** with an **empty** body and no encrypted JSON:

- **GET** on the listener path
- **POST** with an empty body
- Body shorter than the minimum wire length
- No database AES key decrypts probe + payload
- `implantBody` template mismatch
- JSON parse error after decryption
- Implant payload validation error (`option` missing/invalid, required fields, and so on)

### Host validation

After decryption, if the parsed payload is a **single JSON object** with a `host` field, the listener checks that tag exists in the host registry. If not, it responds with HTTP **400** and encrypted JSON:

```json
{ "status": "failure", "error": "Missing host" }
```

JSON **arrays** (batch `output`) skip this pre-check. `last_seen` is still updated from the first array element when it includes `host`.

    <h2 className="api-section-title api-section-title--explanation">Explanation</h2>
    
    This is the main listener path (`endpointPath`). **GET** always returns HTTP `200` with an empty body. **POST** carries encrypted implant traffic as described above.

    Processing order on **POST**: read raw body → optional `implantBody` extraction → decrypt → JSON parse → `parse_implant_payload` → optional host registry check → handler (`main_core` → `main_actions`).

    Requests fall into 3 main modes:

    1. `new` sends the fingerprint and registers the host on first contact
    2. `input` polls the queue for pending commands
    3. `output` sends command results

    There are also optional auxiliary modes:

    1. `kill_task` cancels a queue task
    2. `error` reports a task failure without `option`
