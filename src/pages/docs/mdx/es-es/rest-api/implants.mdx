Implant API expuesta a través del proceso del **listener** HTTP/HTTPS. No es la [REST API de gestión del team server](/docs/rest-api/team-server) que usan el cliente y la automatización.

El implant usa una ruta por canal: `endpointPath` del perfil del listener (normalizada por el servidor para empezar con `/`, sin barra final salvo `/`). En esa ruta se registran **GET** y **POST**.

## Cifrado de la comunicación

Cada petición del implant debe ir cifrada. No es opcional. El team server siempre espera un cuerpo cifrado.

El cifrado usa una clave AES-256 compartida por el implant y el team server. La clave se crea al compilar el implant y se guarda en la base de datos para que el team server pueda descifrar las peticiones entrantes.

**Importante**: cada cuerpo de petición del implant debe contener dos partes:

1. **Challenge** — 9 bytes aleatorios cifrados con la clave AES-256 (siempre exactamente 9 bytes)
2. **Payload** — el JSON de la petición cifrado con la misma clave AES-256

Los dos bloques se concatenan y se envían juntos. Por ejemplo:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** es el challenge
- `{"output": "123"}` es el payload

La salida cifrada sería:

```
000000111111
```

El challenge permite al listener encontrar la clave correcta para descifrar el payload. Como se indicó, el challenge tiene siempre 9 bytes. Eso mantiene la validación rápida sin tocar el payload real, que suele ser mucho mayor.

Si ninguna clave funciona, el listener devuelve HTTP `200` con cuerpo vacío.

En la red, cada segmento cifrado es un **nonce de 12 bytes** seguido del **texto cifrado AES-GCM incluyendo el tag de autenticación de 16 bytes**. El listener trata los primeros **37 bytes** (`12 + 9 + 16`) como el blob de prueba y descifra el resto como el blob del payload. Ambos deben descifrarse con la misma fila de clave de la tabla `AesKeys`.

El tamaño mínimo del cuerpo POST es **65 bytes** (segmento de prueba más al menos un byte de payload). Cuerpos más cortos reciben HTTP `200` con respuesta vacía.

### Plantilla del cuerpo de petición (`implantBody`)

Cuando el canal define `implantBody` (o el legacy `beaconBody`), el cuerpo HTTP en bruto debe coincidir con esa plantilla. El marcador `§content§` es donde van los bytes cifrados. El listener extrae la subcadena que coincide en `§content§` y solo ese fragmento se descifra.

Si `implantBody` está vacío o es exactamente `§content§`, se descifra todo el cuerpo en bruto.

Si hay una plantilla no vacía configurada y el cuerpo no coincide, el listener devuelve HTTP `200` con cuerpo vacío (sin descifrado).

### Plantilla del cuerpo de respuesta (`listenerResponse`)

El JSON del handler se cifra en un solo blob igual que las peticiones del implant. Por defecto ese blob es todo el cuerpo de la respuesta. Cuando `listenerResponse` está definido, los bytes cifrados sustituyen `§content§` en esa plantilla.

Las respuestas cifradas con éxito usan `Content-Type: application/octet-stream`. El estado HTTP es **200** salvo que se indique lo contrario abajo.

### HTTP `200` silencioso (cuerpo vacío)

Estos casos devuelven HTTP **200** con cuerpo **vacío** y sin JSON cifrado:

- **GET** en la ruta del listener
- **POST** con cuerpo vacío
- Cuerpo más corto que la longitud mínima en la red
- Ninguna clave AES de la base de datos descifra el segmento de prueba y el payload
- Desajuste de la plantilla `implantBody`
- Error de parseo JSON tras el descifrado
- Error de validación del payload del implant (`option` ausente o inválida, campos obligatorios, etc.)

### Validación del host

Tras descifrar, si el payload parseado es un **objeto JSON único** con campo `host`, el listener comprueba que ese tag exista en el registro de hosts. Si no, responde HTTP **400** con JSON cifrado:

```json
{ "status": "failure", "error": "Missing host" }
```

Los **arrays** JSON (batch `output`) omiten esta comprobación previa. `last_seen` sigue actualizándose desde el primer elemento del array cuando incluye `host`.

    <h2 className="api-section-title api-section-title--explanation">Explicación</h2>
    
    Esta es la ruta principal del listener (`endpointPath`). **GET** siempre devuelve HTTP `200` con cuerpo vacío. **POST** transporta tráfico cifrado del implant como se describe arriba.

    Orden de procesamiento en **POST**: leer cuerpo en bruto → extracción opcional de `implantBody` → descifrado → parseo JSON → `parse_implant_payload` → comprobación opcional del registro de hosts → handler (`main_core` → `main_actions`).

    Las peticiones se dividen en 3 modos principales:

    1. `new` envía la huella y registra el host en el primer contacto
    2. `input` consulta la cola de comandos pendientes
    3. `output` envía resultados de comandos

    También hay modos auxiliares opcionales:

    1. `kill_task` cancela una tarea de la cola
    2. `error` informa de un fallo de tarea sin `option`
