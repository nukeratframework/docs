HTTP/HTTPS **리스너** 프로세스를 통해 노출되는 임플란트 API입니다. 클라이언트와 자동화가 사용하는 [팀 서버 API](/docs/rest-api/team-server)와는 다릅니다.

임플란트는 채널당 하나의 경로를 사용합니다. 리스너 프로필의 `endpointPath`(서버에서 `/`로 시작하고 `/`를 제외한 끝 슬래시 없이 정규화됨)입니다. 해당 경로에 **GET**과 **POST**가 등록됩니다.

<Callout type="info" title="커스텀 임플란트를 만드시나요?">
  임플란트 API를 설명하는 [커스텀 임플란트](/docs/custom-implants) 고급 가이드를 읽는 것을 권장합니다. 많은 수고를 덜 수 있습니다.
</Callout>

## 통신 암호화

임플란트의 모든 요청은 암호화되어야 합니다. 선택 사항이 아닙니다. 팀 서버는 항상 암호화된 본문을 기대합니다.

암호화는 임플란트와 팀 서버가 공유하는 AES-256 키를 사용합니다. 키는 임플란트 빌드 시 생성되어 데이터베이스에 저장되므로 팀 서버가 수신 요청을 복호화할 수 있습니다.

**중요**: 모든 임플란트 요청 본문에는 두 부분이 포함되어야 합니다.

1. **챌린지** — AES-256 키로 암호화된 9바이트의 난수(항상 정확히 9바이트)
2. **페이로드** — 동일한 AES-256 키로 암호화된 요청 JSON

두 블롭을 이어 붙여 함께 전송합니다. 예:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef**는 챌린지
- `{"output": "123"}`는 페이로드

암호화 결과는 다음과 같습니다.

```
000000111111
```

챌린지는 리스너가 페이로드를 복호화할 올바른 키를 찾을 수 있게 합니다. 위에서 언급했듯이 챌린지는 항상 9바이트입니다. 실제 페이로드는 훨씬 큰 경우가 많으므로, 페이로드를 건드리지 않고 검증을 빠르게 유지합니다.

어떤 키로도 복호화되지 않으면 리스너는 본문이 비어 있는 HTTP `200`을 반환합니다.

전송 시 각 암호화 세그먼트는 **12바이트 nonce** 뒤에 **16바이트 인증 태그를 포함한 AES-GCM 암호문**이 옵니다. 리스너는 처음 **37바이트**(`12 + 9 + 16`)를 탐색 블롭으로 취급하고 나머지를 페이로드 블롭으로 복호화합니다. 둘 다 `AesKeys` 테이블의 동일한 키 행으로 복호화되어야 합니다.

최소 POST 본문 크기는 **65바이트**(탐색 세그먼트 + 최소 1바이트 페이로드)입니다. 더 짧은 본문은 빈 응답과 함께 HTTP `200`을 받습니다.

### 요청 본문 템플릿 (`implantBody`)

채널이 `implantBody`(또는 레거시 `beaconBody`)를 설정하면 원시 HTTP 본문이 해당 템플릿과 일치해야 합니다. 마커 `§content§`가 암호화된 바이트가 들어갈 위치입니다. 리스너는 `§content§`에서 매칭된 부분 문자열만 추출하며, 그 슬라이스만 복호화합니다.

`implantBody`가 비어 있거나 정확히 `§content§`이면 전체 원시 본문을 복호화합니다.

비어 있지 않은 템플릿이 구성되어 있고 본문이 일치하지 않으면 리스너는 복호화 없이 본문이 비어 있는 HTTP `200`을 반환합니다.

### 응답 본문 템플릿 (`listenerResponse`)

핸들러 JSON은 임플란트 요청과 같은 방식으로 단일 블롭으로 암호화됩니다. 기본적으로 그 블롭이 전체 응답 본문입니다. `listenerResponse`가 설정되면 암호화된 바이트가 해당 템플릿의 `§content§`를 대체합니다.

암호화된 성공 응답은 `Content-Type: application/octet-stream`을 사용합니다. 아래에 별도로 적지 않은 한 HTTP 상태는 **200**입니다.

### 조용한 HTTP `200`(빈 본문)

다음 경우 HTTP **200**과 **빈** 본문, 암호화된 JSON 없이 응답합니다.

- 리스너 경로에 대한 **GET**
- 본문이 비어 있는 **POST**
- 최소 전송 길이보다 짧은 본문
- 데이터베이스 AES 키가 탐색 + 페이로드를 복호화하지 못함
- `implantBody` 템플릿 불일치
- 복호화 후 JSON 파싱 오류
- 임플란트 페이로드 검증 오류(`option` 누락/무효, 필수 필드 등)

### 호스트 검증

복호화 후, 파싱된 페이로드가 `host` 필드를 가진 **단일 JSON 객체**이면 리스너는 해당 태그가 호스트 레지스트리에 있는지 확인합니다. 없으면 HTTP **400**과 암호화된 JSON으로 응답합니다.

```json
{ "status": "failure", "error": "Missing host" }
```

JSON **배열**(배치 `output`)은 이 사전 검사를 건너뜁니다. `last_seen`은 첫 번째 배열 요소에 `host`가 포함되어 있으면 여전히 해당 값으로 갱신됩니다.

    메인 리스너 경로(`endpointPath`)입니다. **GET**은 항상 본문이 비어 있는 HTTP `200`을 반환합니다. **POST**는 위에서 설명한 암호화된 임플란트 트래픽을 전달합니다.

    **POST** 처리 순서: 원시 본문 읽기 → 선택적 `implantBody` 추출 → 복호화 → JSON 파싱 → `parse_implant_payload` → 선택적 호스트 레지스트리 확인 → 핸들러(`main_core` → `main_actions`).

    요청은 세 가지 주요 모드로 나뉩니다.

    1. `new` — 지문을 보내고 최초 접속 시 호스트를 등록합니다
    2. `input` — 대기 중인 명령을 위해 큐를 폴링합니다
    3. `output` — 명령 결과를 전송합니다

    선택적 보조 모드도 있습니다.

    1. `kill_task` — 큐 작업을 취소합니다
    2. `error` — `option` 없이 작업 실패를 보고합니다
