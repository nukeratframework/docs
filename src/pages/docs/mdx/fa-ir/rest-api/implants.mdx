API ایمپلنت از طریق فرایند **listener** HTTP/HTTPS در دسترس است. این همان [REST API مدیریت سرور تیم](/docs/rest-api/team-server) نیست که کلاینت و خودکارسازی استفاده می‌کنند.

ایمپلنت برای هر کانال یک مسیر دارد: `endpointPath` از پروفایل listener (در سرور با `/` شروع و بدون اسلش پایانی به‌جز `/` نرمال می‌شود). **GET** و **POST** روی همان مسیر ثبت می‌شوند.

<Callout type="info" title="ایمپلنت سفارشی می‌سازید؟">
  پیشنهاد می‌کنیم راهنمای پیشرفته [ایمپلنت‌های سفارشی](/docs/custom-implants) را بخوانید که API ایمپلنت را توضیح می‌دهد. از دردسر زیاد جلوگیری می‌کند.
</Callout>

## رمزنگاری ارتباط

هر درخواست از ایمپلنت باید رمزنگاری شود. اختیاری نیست. سرور تیم همیشه بدنهٔ رمز شده انتظار دارد.

رمزنگاری با کلید AES-256 مشترک بین ایمپلنت و سرور تیم انجام می‌شود. کلید هنگام ساخت ایمپلنت ایجاد و در پایگاه داده ذخیره می‌شود تا سرور تیم درخواست‌های ورودی را رمزگشایی کند.

**مهم**: هر بدنهٔ درخواست ایمپلنت باید دو بخش داشته باشد:

1. **Challenge** — ۹ بایت تصادفی رمز شده با کلید AES-256 (همیشه دقیقاً ۹ بایت)
2. **Payload** — JSON درخواست رمز شده با همان کلید AES-256

دو بلوb به هم چسبانده و با هم ارسال می‌شوند. مثال:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** challenge است
- `{"output": "123"}` payload است

خروجی رمز شده:

```
000000111111
```

challenge به listener کمک می‌کند کلید درست برای رمزگشایی payload را پیدا کند. همان‌طور که گفته شد challenge همیشه ۹ بایت است تا بدون دست زدن به payload واقعی که اغلب بزرگ‌تر است، اعتبارسنجی سریع بماند.

اگر هیچ کلیدی جواب ندهد، listener HTTP `200` با بدنهٔ خالی برمی‌گرداند.

روی سیم، هر بخش رمز شده **nonce ۱۲ بایتی** و سپس **متن رمز AES-GCM شامل برچسب auth ۱۶ بایتی** است. listener **۳۷ بایت** اول (`12 + 9 + 16`) را probe blob می‌داند و بقیه را payload blob رمزگشایی می‌کند. هر دو باید با همان ردیف کلید از جدول `AesKeys` رمزگشایی شوند.

حداقل اندازهٔ بدنه POST **۶۵ بایت** (بخش probe به‌علاوه حداقل یک بایت payload) است. بدنه‌های کوتاه‌تر HTTP `200` با پاسخ خالی می‌گیرند.

### قالب بدنه درخواست (`implantBody`)

وقتی کانال `implantBody` (یا legacy `beaconBody`) را تنظیم کند، بدنهٔ خام HTTP باید با آن قالب مطابقت داشته باشد. نشانگر `§content§` جایی است که بایت‌های رمز شده قرار می‌گیرند. listener زیررشتهٔ matched در `§content§` را استخراج می‌کند و فقط همان slice رمزگشایی می‌شود.

اگر `implantBody` خالی یا دقیقاً `§content§` باشد، کل بدنهٔ خام رمزگشایی می‌شود.

اگر قالب غیرخالی پیکربندی شده و بدنه مطابقت نداشته باشد، listener HTTP `200` با بدنهٔ خالی (بدون رمزگشایی) برمی‌گرداند.

### قالب بدنه پاسخ (`listenerResponse`)

JSON handler مثل درخواست‌های ایمپلنت در یک blob رمز می‌شود. پیش‌فرض آن blob کل بدنه پاسخ است. وقتی `listenerResponse` تنظیم باشد، بایت‌های رمز شده `§content§` را در آن قالب جایگزین می‌کنند.

پاسخ‌های رمز شده موفق `Content-Type: application/octet-stream` دارند. وضعیت HTTP **200** است مگر خلاف آن ذکر شده باشد.

### HTTP `200` خاموش (بدنه خالی)

این موارد HTTP **200** با بدنه **خالی** و بدون JSON رمز شده برمی‌گردانند:

- **GET** روی مسیر listener
- **POST** با بدنه خالی
- بدنه کوتاه‌تر از حداقل طول سیم
- هیچ کلید AES پایگاه داده probe + payload را رمزگشایی نکند
- عدم تطابق قالب `implantBody`
- خطای parse JSON پس از رمزگشایی
- خطای اعتبارسنجی payload ایمپلنت (`option` گم/نامعتبر، فیلدهای الزامی و غیره)

### اعتبارسنجی host

پس از رمزگشایی، اگر payload parse شده **یک شی JSON** با فیلد `host` باشد، listener بررسی می‌کند آن tag در رجیstry host وجود دارد. اگر نباشد HTTP **400** با JSON رمز شده:

```json
{ "status": "failure", "error": "Missing host" }
```

**آرایه‌های** JSON (batch `output`) این پیش‌بررسی را رد می‌کنند. `last_seen` همچنان از اولین عنصر آرایه وقتی `host` دارد به‌روز می‌شود.

    این مسیر اصلی listener (`endpointPath`) است. **GET** همیشه HTTP `200` با بدنه خالی برمی‌گرداند. **POST** ترافیک رمز شده ایمپلنت را طبق بالا حمل می‌کند.

    ترتیب پردازش **POST**: خواندن بدنه خام → استخراج اختیاری `implantBody` → رمزگشایی → parse JSON → `parse_implant_payload` → بررسی اختیاری رجیstry host → handler (`main_core` → `main_actions`).

    درخواست‌ها سه حالت اصلی دارند:

    1. `new` اثر انگشت را می‌فرستد و host را در اولین تماس ثبت می‌کند
    2. `input` صف را برای دستورات در انتظار poll می‌کند
    3. `output` نتایج دستور را می‌فرستد

    حالت‌های کمکی اختیاری:

    1. `kill_task` کار صف را لغو می‌کند
    2. `error` شکست task را بدون `option` گزارش می‌کند
