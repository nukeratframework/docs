Чтобы имплант обменивался данными с сервером команды, для него должен быть настроен канал.

Сейчас доступны две категории каналов:
- HTTP/HTTPS
- Custom

## Канал HTTP/HTTPS

Это самый простой и распространённый канал. Помимо URL, по которому имплант достучится до сервера, дополнительная настройка не требуется.

При создании канала можно изменить и более продвинутые параметры, например:

- путь в URL (пример: `https://example.com/path` → `https://example.com/path/custom`)
- заголовки ответа
- пользовательские шаблоны тела для запросов импланта и ответов listener

## Пользовательский канал (Custom)

Это самый сложный, но и самый гибкий тип канала. Он нужен, когда требуется очень специфичный обмен, например:

- Telegram
- Discord
- Dropbox

Готовых пресетов нет — всё настраивается вручную, включая этап сборки импланта, где нужно написать свой фрагмент кода для обмена с каналом.

В интерфейсе создания нет пункта «custom channel»: канал собирается вручную. Подробнее — в разделе [Custom C2](/docs/custom-channels).

## А другие типы каналов?

В других фреймворках по-прежнему встречаются DNS, DoH, mTLS и другие варианты. Мы остановились на этих двух типах, чтобы соответствовать текущим трендам — в том числе запросу на интеграцию с внешними сервисами вроде Telegram, Google Drive и т. п.

Официально добавлять новые типы каналов в будущем не планируется.

Если нужен конкретный тип, например DNS, его придётся реализовать через **Custom Channel**.

## Создание HTTP-канала

HTTP-канал (без SSL) создаётся проще всего. Выполните шаги ниже:

  <Steps>
    <Step>
      ### Открыть вкладку listeners
      Откройте **NukeRat** > **Listeners** > **Add**.
    </Step>
    <Step>
      ### Заполнить поля
      <ImageZoom src={listenerForm} alt="Listener Form" className="h-[30rem] tutorial_img" style={{ marginLeft: 0, marginRight: 0, display: 'block' }} />
      - **Name**: имя, по которому listener легко узнать.
      - **Type**: выберите `Channel`
      - **Channel**: `http` или `https`
      - **Server**: сервер команды, на котором будет создан listener (его нужно настроить заранее)
      - **Port to open**: порт, который будет использоваться
    </Step>
    <Step>
      ### Нажать **Create**
      Если всё верно, listener появится в списке на вкладке listeners.
      <ImageZoom src={listenerOk} alt="Listener Ok" className="h-[6.5rem] tutorial_img" style={{ marginLeft: 0, marginRight: 0, display: 'block' }} />
    </Step>
  </Steps>

После создания имплант может обмениваться данными через настроенный канал.

HTTP-канал (без SSL) шифрует тела запросов импланта и ответов listener общим ключом AES 256, заданным при сборке импланта. Даже при перехвате HTTP-сессии без ключа содержимое тел остаётся нечитаемым. Как выглядит трафик в сети — в разделе [Шифрование обмена](/docs/rest-api/implants#шифрование-обмена).

## HTTPS и сертификаты

Для SSL при создании listener выберите `https` в поле **Channel**. Ниже поля порта появится секция **Certificate**. В **Source** укажите self signed или manual.

Самоподписанные сертификаты NukeRat генерирует через `openssl`; можно настроить срок, CN, SAN, тип ключа и другие параметры.

В placeholder некоторых полей указаны примеры. Их не стоит копировать буквально — по совпадению подписи сертификата возможна детекция.

Для ручной загрузки вставьте или загрузите PEM сертификата и закрытого ключа (например, от провайдера вроде Namecheap).

Как и HTTP без SSL, HTTPS-канал использует то же шифрование AES 256 для тел импланта. TLS защищает транспорт, а тела остаются зашифрованными даже при инспекции SSL/TLS.

## Расширенные настройки

У каналов HTTP/HTTPS в блоке **Advanced** доступны поля:

- **Endpoint path**: путь URL, по которому имплант обращается к каналу
- **Response headers**: заголовки ответа канала
- **Custom body**: пресет (`off`, `custom` или встроенные примеры `json` и `xml`) и при необходимости шаблоны **Listener response** и **Implant request**, если custom body не `off`

## Custom body

По умолчанию обмен между имплантом и сервером простой: строка шифруется и попадает в тело, например:

```http
POST /api HTTP/1.1
Host: example.com

U2FsdGVkX1/Z8mN3kL9qP2vX7dQ4jK1mR5sT8uW2xY3aB6cD9e...
```

Обратите внимание: тело — просто блок зашифрованных данных без заданной структуры. С custom body можно задать общий формат между имплантом и сервером, например:

**Ответ сервера:**
```http
{
  "status": "ok",
  "data": "§content§"
}
```

**Запрос импланта:**
```http
{
  "type": "telemetry",
  "event": "sync",
  "payload": "§content§"
}
```

После настройки канал отправляет ответы в заданном формате и ожидает тот же формат в запросах импланта.

В интерфейсе создания канала есть примеры custom body, но использовать их «как есть» не рекомендуется — возможна детекция по сигнатуре тела.

### Замечания

1. Чтобы имплант работал корректно, при создании импланта повторите те же шаблоны **Listener response** и **Implant request**. Listener читает `implantBody` и оборачивает ответы через `listenerResponse` во время работы (см. [Шаблон тела запроса (implantBody)](/docs/rest-api/implants#шаблон-тела-запроса-implantbody)).
2. На каналах HTTP/HTTPS, если `implantBody` пуст или ровно `§content§`, шифруется всё сырое тело запроса. При пользовательской структуре шифруется только фрагмент `§content§`. Listener извлекает его перед расшифровкой.
