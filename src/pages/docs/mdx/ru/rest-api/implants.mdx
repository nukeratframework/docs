Implant API доступен через процесс HTTP/HTTPS **listener**. Это не [REST API управления team server](/docs/rest-api/team-server), которым пользуются клиент и автоматизация.

У импланта один путь на канал: `endpointPath` из профиля listener (сервер нормализует его так, чтобы путь начинался с `/`, без завершающего слэша, кроме `/`). На этом пути регистрируются **GET** и **POST**.

## Шифрование обмена

Каждый запрос от импланта должен быть зашифрован. Это обязательно. Team server всегда ожидает зашифрованное тело.

Шифрование использует ключ AES-256, общий для импланта и team server. Ключ создаётся при сборке импланта и сохраняется в базе, чтобы team server мог расшифровывать входящие запросы.

**Важно**: тело каждого запроса импланта должно содержать две части:

1. **Challenge** — 9 случайных байт, зашифрованных ключом AES-256 (всегда ровно 9 байт)
2. **Payload** — JSON запроса, зашифрованный тем же ключом AES-256

Оба блока склеиваются и отправляются вместе. Например:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** — challenge
- `{"output": "123"}` — payload

Зашифрованный результат:

```
000000111111
```

Challenge нужен, чтобы listener подобрал ключ для расшифровки payload. Как указано выше, challenge всегда 9 байт — проверка быстрая и не затрагивает основной payload, который часто намного больше.

Если ни один ключ не подошёл, listener возвращает HTTP `200` с пустым телом.

В канале каждый зашифрованный сегмент — **nonce 12 байт**, затем **шифротекст AES-GCM с 16-байтовым auth tag**. Listener считает первые **37 байт** (`12 + 9 + 16`) пробным блоком и расшифровывает остаток как payload. Оба сегмента должны расшифроваться одной записью из таблицы `AesKeys`.

Минимальный размер тела POST — **65 байт** (пробный сегмент плюс хотя бы один байт payload). Более короткие тела получают HTTP `200` с пустым ответом.

### Шаблон тела запроса (`implantBody`)

Если у канала задан `implantBody` (или устаревший `beaconBody`), сырое HTTP-тело должно соответствовать шаблону. Маркер `§content§` — место для зашифрованных байт. Listener извлекает подстроку по `§content§` и расшифровывает только её.

Если `implantBody` пуст или равен `§content§`, расшифровывается всё тело.

При непустом шаблоне, если тело не совпало, listener отвечает HTTP `200` с пустым телом (без расшифровки).

### Шаблон тела ответа (`listenerResponse`)

JSON обработчика шифруется одним блоком так же, как запросы импланта. По умолчанию этот блок — всё тело ответа. Если задан `listenerResponse`, зашифрованные байты подставляются вместо `§content§` в шаблон.

Успешные зашифрованные ответы используют `Content-Type: application/octet-stream`. HTTP-статус **200**, если ниже не указано иное.

### «Тихий» HTTP `200` (пустое тело)

В этих случаях возвращается HTTP **200** с **пустым** телом и без зашифрованного JSON:

- **GET** на путь listener
- **POST** с пустым телом
- Тело короче минимальной длины на проводе
- Ни один AES-ключ из БД не расшифровал пробный блок и payload
- Несовпадение шаблона `implantBody`
- Ошибка разбора JSON после расшифровки
- Ошибка валидации payload импланта (отсутствует или неверный `option`, обязательные поля и т. д.)

### Проверка хоста

После расшифровки, если payload — **один JSON-объект** с полем `host`, listener проверяет, что такой tag есть в реестре хостов. Если нет — HTTP **400** и зашифрованный JSON:

```json
{ "status": "failure", "error": "Missing host" }
```

JSON-**массивы** (пакетный `output`) эту предварительную проверку пропускают. `last_seen` по-прежнему обновляется из первого элемента массива, если в нём есть `host`.

    <h2 className="api-section-title api-section-title--explanation">Пояснение</h2>
    
    Это основной путь listener (`endpointPath`). **GET** всегда возвращает HTTP `200` с пустым телом. **POST** передаёт зашифрованный трафик импланта, как описано выше.

    Порядок обработки **POST**: чтение сырого тела → при необходимости извлечение по `implantBody` → расшифровка → разбор JSON → `parse_implant_payload` → при необходимости проверка реестра хостов → обработчик (`main_core` → `main_actions`).

    Запросы делятся на три основных режима:

    1. `new` — отправляет отпечаток и регистрирует хост при первом контакте
    2. `input` — опрашивает очередь на ожидающие команды
    3. `output` — отправляет результаты команд

    Есть и необязательные вспомогательные режимы:

    1. `kill_task` — отменяет задачу в очереди
    2. `error` — сообщает об ошибке задачи без поля `option`
