HTTP/HTTPS **リスナー** プロセス経由で公開されるインプラント API です。クライアントと自動化が使う [チームサーバー管理 REST API](/docs/rest-api/team-server) ではありません。

インプラントはチャネルごとに 1 パスを使います。リスナープロファイルの `endpointPath`（サーバー側で `/` 始まり、末尾スラッシュなし `/` を除いて正規化）です。そのパスに **GET** と **POST** が登録されます。

<Callout type="info" title="カスタムインプラントを構築しますか？">
  インプラント API を解説する [カスタムインプラント](/docs/custom-implants) の高度なガイドを読むことをおすすめします。多くの手間を省けます。
</Callout>

## 通信の暗号化

インプラントからのすべてのリクエストは暗号化必須です。省略できません。チームサーバーは常に暗号化されたボディを期待します。

暗号化には、インプラントとチームサーバーが共有する AES-256 キーを使います。キーはインプラントビルド時に作成されデータベースに保存され、チームサーバーが受信リクエストを復号できます。

**重要**: すべてのインプラントリクエストボディには次の 2 部分が含まれます。

1. **チャレンジ** — AES-256 キーで暗号化した 9 バイトの乱数（常に正確に 9 バイト）
2. **ペイロード** — 同じ AES-256 キーで暗号化したリクエスト JSON

2 つの暗号化ブロックを連結して一緒に送ります。例:

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** がチャレンジ
- `{"output": "123"}` がペイロード

暗号化結果は次のとおりです。

```
000000111111
```

チャレンジは、リスナーがペイロードを復号する正しいキーを見つけるために存在します。上記のとおりチャレンジは常に 9 バイトです。実際のペイロードははるかに大きいことが多いため、ペイロードに触れずに検証を高速に保てます。

どのキーでも復号できない場合、リスナーは HTTP `200` と空ボディを返します。

ワイヤ上では、各暗号化セグメントは **12 バイト nonce** の後に **16 バイト認証タグを含む AES-GCM 暗号文** が続きます。リスナーは先頭 **37 バイト**（`12 + 9 + 16`）をプローブ用ブロックとして扱い、残りをペイロード用ブロックとして復号します。両方とも `AesKeys` テーブルの同一キー行で復号する必要があります。

POST ボディの最小サイズは **65 バイト**（プローブセグメント + ペイロード最低 1 バイト）です。それより短いボディは HTTP `200` と空レスポンスになります。

### リクエストボディテンプレート（`implantBody`）

チャネルが `implantBody`（またはレガシーの `beaconBody`）を設定している場合、生 HTTP ボディはそのテンプレートと一致する必要があります。マーカー `§content§` が暗号化バイトを置く位置です。リスナーは `§content§` でマッチした部分文字列だけを抽出し、そのスライスのみ復号します。

`implantBody` が空、または正確に `§content§` の場合、生ボディ全体を復号します。

空でないテンプレートが設定されていてボディが一致しない場合、リスナーは復号せず HTTP `200` と空ボディを返します。

### レスポンスボディテンプレート（`listenerResponse`）

ハンドラー JSON はインプラントリクエストと同じ方法で 1 つの暗号化ブロックに暗号化されます。デフォルトではそのブロックがレスポンスボディ全体です。`listenerResponse` が設定されている場合、暗号化バイトがテンプレート内の `§content§` を置き換えます。

暗号化された成功レスポンスは `Content-Type: application/octet-stream` を使います。特記がない限り HTTP ステータスは **200** です。

### サイレント HTTP `200`（空ボディ）

次の場合は HTTP **200** と **空** ボディ、暗号化 JSON なしで応答します。

- リスナーパスへの **GET**
- 空ボディの **POST**
- 最小ワイヤ長より短いボディ
- データベース AES キーがプローブ + ペイロードを復号できない
- `implantBody` テンプレート不一致
- 復号後の JSON パースエラー
- インプラントペイロード検証エラー（`option` 欠落/無効、必須フィールドなど）

### ホスト検証

復号後、パースしたペイロードが `host` フィールドを持つ **単一 JSON オブジェクト** の場合、リスナーはその `tag` がホストレジストリに存在するか確認します。存在しなければ HTTP **400** と暗号化 JSON で応答します。

```json
{ "status": "failure", "error": "Missing host" }
```

JSON **配列**（バッチ `output`）はこの事前チェックをスキップします。`last_seen` は、最初の配列要素に `host` が含まれる場合、その値から更新されます。

    <h2 className="api-section-title api-section-title--explanation">説明</h2>
    
    メインリスナーパス（`endpointPath`）です。**GET** は常に HTTP `200` と空ボディを返します。**POST** は上記の暗号化インプラントトラフィックを運びます。

    **POST** の処理順: 生ボディ読み取り → 任意の `implantBody` 抽出 → 復号 → JSON パース → `parse_implant_payload` → 任意のホストレジストリチェック → ハンドラー（`main_core` → `main_actions`）。

    リクエストは主に 3 モードに分かれます。

    1. `new` — フィンガープリントを送り、初回接触でホストを登録
    2. `input` — 保留コマンドのためにキューをポーリング
    3. `output` — コマンド結果を送信

    任意の補助モードもあります。

    1. `kill_task` — キュータスクをキャンセル
    2. `error` — `option` なしでタスク失敗を報告
