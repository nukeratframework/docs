Implant API 由 HTTP/HTTPS **监听器（listener）** 进程对外提供。这与客户端和自动化所使用的[团队服务器管理 REST API](/docs/rest-api/team-server) 不是同一套接口。

每个通道对应植入体的一个路径：即监听器配置中的 `endpointPath`（服务端会规范为以 `/` 开头，除 `/` 外不以 `/` 结尾）。该路径上同时注册 **GET** 与 **POST**。

## 通信加密

植入体发出的每个请求都必须加密，没有例外。团队服务器始终期望收到加密请求体。

加密使用植入体与团队服务器共享的 AES-256 密钥。密钥在构建植入体时生成并写入数据库，以便团队服务器解密入站请求。

**重要**：每个植入体请求体必须包含两部分：

1. **Challenge（挑战）** — 用 AES-256 密钥加密的 9 个随机字节（始终恰好 9 字节）
2. **Payload（载荷）** — 用同一 AES-256 密钥加密的请求 JSON

两段密文拼接后一并发送。例如：

```
abcdef = 000000
{"output": "123"} = 111111
```

- **abcdef** 表示 challenge
- `{"output": "123"}` 表示 payload

加密后的结果为：

```
000000111111
```

Challenge 用于让监听器匹配正确的密钥以解密 payload。如上所述，challenge 固定为 9 字节，校验很快且无需触碰通常大得多的真实 payload。

若没有密钥能解密，监听器返回 HTTP `200` 且响应体为空。

线路上每个加密段为 **12 字节 nonce**，后接 **含 16 字节 auth tag 的 AES-GCM 密文**。监听器将前 **37 字节**（`12 + 9 + 16`）视为探测块，其余部分作为 payload 块解密。两段必须使用 `AesKeys` 表中的同一密钥行解密。

POST 请求体的最小长度为 **65 字节**（探测段加至少 1 字节 payload）。更短的主体同样返回 HTTP `200` 且响应为空。

### 请求体模板 (`implantBody`)

当通道配置了 `implantBody`（或旧字段 `beaconBody`）时，原始 HTTP 体必须符合该模板。标记 `§content§` 处放置加密字节。监听器提取 `§content§` 匹配到的子串，仅对该片段解密。

若 `implantBody` 为空或恰好为 `§content§`，则解密整个原始请求体。

若配置了非空模板而请求体不匹配，监听器返回 HTTP `200` 且响应体为空（不进行解密）。

### 响应体模板（`listenerResponse`）

处理程序返回的 JSON 与植入体请求一样加密为单个 blob。默认该 blob 即为整个响应体。设置 `listenerResponse` 时，加密字节替换模板中的 `§content§`。

成功的加密响应使用 `Content-Type: application/octet-stream`。HTTP 状态为 **200**，除非下文另有说明。

### 静默 HTTP `200`（空响应体）

以下情况返回 HTTP **200**、**空**响应体且无加密 JSON：

- 对监听器路径的 **GET**
- **POST** 且请求体为空
- 请求体短于线路上的最小长度
- 数据库中没有任何 AES 密钥能解密探测块与 payload
- `implantBody` 模板不匹配
- 解密后 JSON 解析失败
- 植入体 payload 校验失败（`option` 缺失或无效、必填字段缺失等）

### 主机校验

解密后，若 payload 为带 `host` 字段的**单个 JSON 对象**，监听器会检查该 tag 是否存在于主机注册表。若不存在，返回 HTTP **400** 及加密 JSON：

```json
{ "status": "failure", "error": "Missing host" }
```

JSON **数组**（批量 `output`）跳过此预检。若首个数组元素包含 `host`，仍会据此更新 `last_seen`。

    <h2 className="api-section-title api-section-title--explanation">说明</h2>
    
    这是监听器的主路径（`endpointPath`）。**GET** 始终返回 HTTP `200` 且响应体为空。**POST** 承载如上所述的加密植入体流量。

    **POST** 处理顺序：读取原始 body → 按 `implantBody` 提取（若配置）→ 解密 → JSON 解析 → `parse_implant_payload` → 主机注册表校验（若需要）→ 处理器（`main_core` → `main_actions`）。

    请求主要分为三种模式：

    1. `new` — 发送指纹并在首次联络时注册主机
    2. `input` — 轮询队列中的待执行命令
    3. `output` — 回传命令执行结果

    另有可选的辅助模式：

    1. `kill_task` — 取消队列中的任务
    2. `error` — 在无 `option` 字段时上报任务失败
